## 1. 집계 숫자 확인 (요청 1)

**결론: 검증 누락이나 중복이 아닙니다. 73과 74는 둘 다 맞는 숫자이고, 보고서 설명이 빠져 있었습니다.**

비교 SQL(`verify_rollback`)의 항목 수는 고정이 아닙니다. '원래 있던 행'과 '지금 있는 행'을 합쳐서 세기 때문입니다.

| 구분 | 변경 전 / 되돌린 뒤 | 적용 후 |
|---|---|---|
| 함수 | 42 (PASS 42) | 42 (FAIL 42 — 42개 모두 search_path가 바뀌므로) |
| 정책 | 25 (PASS 25) | 25 (PASS 24, FAIL 1 — `places: 추가 요청`) |
| 기본 권한 | **6** (PASS 6) | **7** (PASS 5, FAIL 2) |
| **합계** | **73** (PASS 73) | **74** (PASS 29, FAIL 45) |

- 기본 권한이 6 → 7이 되는 이유: 마이그레이션의 `alter default privileges for role postgres revoke execute on functions from public`이 **전역(스키마 무관) 기본 권한 행을 새로 하나 만듭니다.**
  - 조사 당시에는 이 행이 없었습니다(= PUBLIC 기본 허용 상태).
  - 그래서 적용 후에는 '원래 없던 행이 생김'으로 1건 더 잡힙니다.
- 적용 후 기본 권한 FAIL 2건의 내용:
  - `f/public`: anon·authenticated가 빠짐(의도한 변경)
  - `f/-`(전역): 새로 생긴 행(의도한 변경)
- 되돌리면 이 행이 사라져 다시 6행, 합계 73이 됩니다.
- [테스트 DB] 방금 다시 실행해 구분별 개수를 확인했습니다: 변경 전 42/25/6, 적용 후 42/25/7, 되돌린 뒤 42/25/6.
- 역할 테스트 82건의 구분별 개수도 결과 파일에서 다시 셌습니다: 비로그인 32, 익명 로그인 20, 일반 회원 12, 차단 사용자 2, 운영자 13, 관리 도구 2(SQL 편집기 1, service_role 1), 크론 1 = 82.

4차 보고서에서 정정할 문장: "적용 후 비교: 45개 FAIL, 정책 24개·기본 권한 5행 PASS" → "적용 후에는 전역 기본 권한 행이 1개 생겨 항목이 74개가 됨(FAIL 45 = 함수 42 + 기본 권한 2 + 정책 1, PASS 29 = 정책 24 + 기본 권한 5)".

### 2.2 [운영·읽기] 적용 전 기준선 (2026-11-12 19:40)
`docs/security-tests-2026-11-12/api_path_test.js`의 읽기 전용 부분을 ppaxse.com에서 공개 키로 실행했습니다(18건, 쓰기 없음).

- 정상이어야 하는 4건(ppx_stats, ppx_event_status, is_admin, 지도 데이터 조회): 모두 200
- **비로그인인데 실행된 함수 8개**: `ppx_guard`, `my_pending_count`, `my_pending_reports`, `start_claim`, `finish_claim`, `ppx_event_week`, `ppx_event_start`, `ppx_event_draw_at`
- `admin_event_entries`는 비로그인 요청이 함수 본문까지 들어가 "운영자만 볼 수 있어요"로 거절됨(PUBLIC 경로가 열려 있다는 뜻)
- 이미 닫혀 있던 것: `ppx_burst_guard`, `ppx_is_member`, `admin_visit_stats`, `admin_type_votes` → 401 / 42501
- 비로그인 세차장 등록: 401 / 42501

이 결과는 테스트 DB의 '변경 전' 역할 테스트와 **항목별로 같습니다.** 테스트 DB가 운영의 실제 요청 동작을 제대로 재현하고 있다는 근거입니다.
적용 후 기대: 위 8개와 `admin_event_entries`가 모두 `42501 permission denied`.

### 2.3 [운영·읽기, 준비됨] `auth.jwt() ->> 'role'`의 간접 증거 — `supabase/preflight_2026-11-12.sql`
- 한마디 등록 트리거(`place_comments_before_insert`)는 2026-11-09부터 **같은 판별식**을 운영에서 쓰고 있습니다(SECURITY DEFINER).
- 판별이 실패하면 그 트리거는 일찍 끝나서 `user_id`가 비게 됩니다. 이용자는 `user_id` 열에 직접 쓸 권한이 없습니다(열 권한 조사로 확인).
- 따라서 **11-09 이후 한마디의 `user_id`가 모두 채워져 있으면, 실제 authenticated 요청에서 판별이 동작했다는 증거**입니다.
- 이 SQL은 SELECT 1개이고, `auth.jwt()`·`auth.uid()`의 운영 정의와 최근 크론 실행 기록도 함께 보여 줍니다.
- 한계: 11-09 이후 한마디가 0건이면 증거가 되지 않습니다. 이 경우 **[미검증]**으로 남깁니다.

### 2.4 판별이 틀렸을 때의 영향 (실패 모드)
- authenticated 요청에서 role이 비어 나오는 경우(예상하지 않는 상황)
  - `places`: 새 등록 정책(대기 + 본인만 통과)이 조작된 값을 거부합니다. 즉 이중 방어가 됩니다.
  - `place_reports`, `place_checks`: 값 고정과 횟수 제한이 빠집니다. → **적용 직후 2.5의 (2)로 바로 확인하고, 틀리면 즉시 롤백**
- anon 요청: 어느 쪽이든 등록 정책이 `to authenticated`라 거부됩니다.
