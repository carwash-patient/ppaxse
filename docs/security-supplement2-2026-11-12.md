## 0. 먼저 밝혀 둘 한계: '별도 Supabase 테스트 프로젝트'에서는 검증하지 못했습니다

요청 2는 별도 Supabase 테스트 프로젝트에서의 검증이었습니다. **이 조건은 충족하지 못했습니다.**

- Supabase 프로젝트를 새로 만드는 일은 운영자 계정에서 해야 하는 작업이라, Claude가 임의로 만들지 않았습니다.
- 대신 실제 PostgREST를 작업 공간에 띄우려 했지만, 바이너리를 받을 수 없었습니다(GitHub 릴리스·Docker·패키지 저장소가 이 작업 공간에서 차단됨).
- 그래서 **실제 PostgreSQL 17.11 + 직접 만든 '요청 흉내 서버'**(`pgrst_emu.js`)로 검증했습니다.

| 구분 | 이번 검증에서 실제인 것 | 흉내인 것 |
|---|---|---|
| DB | PostgreSQL 17.11(운영과 같은 버전). 함수 본문·정책·권한·`auth.uid()`/`auth.jwt()` 정의가 운영과 일치(이전 보고서) | — |
| 요청 처리 | 요청마다 `set local role anon/authenticated` + `request.jwt.claims` 설정 후 SQL 실행. GET은 읽기 전용 트랜잭션. RLS·트리거·함수 권한은 PostgreSQL이 실제로 판정 | HTTP 계층(주소 해석, 상태 코드 변환, JSON 출력)은 PostgREST 문서를 따라 직접 구현 |
| 로그인 | — | 익명 가입·토큰 갱신은 GoTrue가 아니라 흉내(같은 모양의 JWT 발급, `auth.users`에 행 추가) |

따라서 아래 결과는 **'스크립트의 논리 + DB 동작'은 확인**했지만, **'실제 Supabase API 게이트웨이·PostgREST·GoTrue를 거친 동작'은 여전히 [미검증]**입니다. 이 항목은 PASS로 표시하지 않습니다.

**실제 Supabase에서 검증하려면** (운영자 결정 사항):
1. 운영자가 무료 테스트 프로젝트를 하나 만듭니다.
2. SQL 편집기에서 이 브랜치의 `supabase/schema.sql`을 Run 합니다(적용 후 상태가 됨).
3. Auth에서 익명 로그인을 켭니다.
4. 프로젝트 주소와 공개 키를 알려주시면 같은 테스트(`run_flow_a.js`, `run_flow_bc.js`의 요청들)를 그 프로젝트를 상대로 실행합니다.
