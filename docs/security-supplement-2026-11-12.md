### 1.4 특별히 본 세 가지 기능

**가입 전 기록 이어받기** [코드 조사 + 테스트 DB]
- 흐름: 익명으로 제보 → 로그인/가입 버튼 → `prepareClaim()`이 익명 세션으로 `start_claim` → 번호를 기기에 저장 → 로그인 성공 → `me()` → `finishClaim()`이 회원 세션으로 `finish_claim`.
- 두 호출 모두 authenticated 역할이며, 그 권한은 유지됩니다. [테스트 DB] 익명 `start_claim` 정상, 회원 `finish_claim` 정상.
- 예외 상황(세션이 만료돼 요청이 비로그인으로 나가는 경우):
  - 변경 전: `start_claim`은 빈 값을 돌려주고 끝납니다. `finish_claim`은 0을 돌려주는데, 화면은 이를 성공으로 보고 **번호표를 지워 버립니다**(이어받기 기회를 잃음).
  - 변경 후: 둘 다 오류(권한 없음)가 됩니다. `prepareClaim`은 오류를 무시하도록 돼 있고, `finishClaim`은 오류면 번호표를 **지우지 않고 남겨** 다음 로그인 때 다시 시도합니다.
  - 즉 기능이 깨지지 않고, 이 예외 상황에서는 오히려 기록을 덜 잃습니다.
- **[미검증]**: 실제 사이트에서 '익명 제보 → 가입 → 마이페이지에 보임'은 적용 후 체크리스트 9번으로 확인.

**이벤트 표시** [코드 조사 + 운영·읽기]
- 화면은 `ppx_event_status` 하나만 부릅니다. 이 함수는 소유자 권한으로 돌며 안에서 `ppx_event_week`·`ppx_event_start`·`ppx_is_member`·`ppx_entry_valid`를 부릅니다. 안쪽 함수에 호출자 권한은 필요 없습니다.
- 운영 증거: `ppx_is_member`·`ppx_entry_valid`는 **지금도 비로그인에게 닫혀 있는데**(19:55 기준선: `ppx_is_member` → 42501) `ppx_event_status`는 200으로 정상입니다. 같은 구조이므로 `ppx_event_week` 등을 닫아도 같습니다.
- [테스트 DB] 적용 후 비로그인 `ppx_event_status` 정상.

**응모** [코드 조사 + 테스트 DB]
- 화면은 `ppx_enter_event`(authenticated 유지)만 부릅니다. 안에서 쓰는 `ppx_event_week`·`ppx_event_start`는 소유자 권한으로 실행됩니다.
- **[미검증]**: 테스트 DB의 역할 테스트는 응모 성공 경로를 직접 실행하지 않았습니다(이벤트 시작일 11-14 전이라 "11월 14일부터" 안내로 끝남).
  - 근거는 '소유자 권한 함수 안의 호출은 호출자 권한이 필요 없다'는 PostgreSQL 동작과, 같은 구조인 `ppx_event_status`·`ppx_auto_draw`가 통과한 점입니다.
  - 11-14 이후 체크리스트 8번으로 실제 확인이 필요합니다.

## 2. API 점검 스크립트의 '읽기 전용' 재검증 (요청 2)

### 2.1 정정: 19:40의 18건은 '읽기 전용'이 아니었습니다
지난 보고서에서 "공개 API 읽기 요청 18건, 쓰기 없음"이라고 썼습니다. 정확하지 않았습니다.
- 18건 중 17건은 RPC **POST**, 1건은 조회 GET, 그리고 **`places` 등록 POST 1건**이 들어 있었습니다.
- 그 가운데 `start_claim`·`finish_claim`은 본문에 INSERT/DELETE/UPDATE가 있는 함수입니다.
- 실제로 일어난 일(함수 본문과 테스트 DB 재현으로 확인):

| 요청 (비로그인) | 결과 | 데이터 변화 |
|---|---|---|
| `start_claim` POST | 200, 빈 값 | 없음 — 본문 첫 조건(`auth.uid() is null` → `return null`)에서 끝남. DELETE/INSERT 문에 도달하지 않음 |
| `finish_claim` POST | 200, 0 | 없음 — 첫 조건(`auth.uid() is null` → `return 0`)에서 끝남 |
| `ppx_burst_guard` POST | 42501 | 없음 — 실행 전 거부 |
| `places` 등록 POST | 42501 (트리거 안에서 거부) | **행은 저장되지 않음. 단, 세차장 번호(ID) 1개가 건너뛰어졌을 가능성이 높음** |
| 나머지 RPC 13건 | 200 또는 거부 | 없음 — 본문에 쓰기 문장이 없음 |

- **번호 건너뜀**: PostgreSQL은 등록이 거부돼도 이미 뽑은 번호를 되돌리지 않습니다.
  - [테스트 DB] 같은 요청을 재현하니 번호가 1 올라갔고 행은 0건이었습니다.
  - 영향: 다음에 등록되는 세차장 번호가 하나 건너뜁니다. 데이터·기능 영향은 없습니다.
  - 운영에서 실제로 건너뛰었는지는 `preflight` SQL의 `places_id` 항목으로 확인할 수 있게 했습니다 → 실행 전까지 **[미검증]**.
- 그 밖에 확인한 것: 점검용으로 연 `privacy.html`은 `ppx.js`를 불러오지 않아 방문 기록(`ppx_track`)을 남기지 않았습니다.
- **판단 잘못**: 쓰기 가능 함수와 등록 시도를 '거부될 것'이라는 이유로 읽기 전용이라 불렀습니다. 운영 쓰기 금지 원칙에 비춰 넣지 말았어야 할 요청이었습니다.

### 2.2 함수 본문 조사 (요청하신 8개 + 스크립트가 부른 나머지)
본문은 운영과 해시로 일치함을 확인한 저장소 정의입니다. volatility는 저장소 정의로 만든 [테스트 DB] 값이며, **운영 값은 `preflight` SQL의 `function_volatility`로 확인 예정 → [미검증]**.

| 함수 | volatility | 본문의 쓰기·부작용 | 비로그인으로 불렀을 때 |
|---|---|---|---|
| `start_claim` | VOLATILE | **DELETE**(지난 번호표), **INSERT**(새 번호표) — 익명 로그인 사용자일 때만 | 첫 조건에서 끝남, 쓰기 없음 |
| `finish_claim` | VOLATILE | **DELETE** 1 + **UPDATE** 6 + DELETE 3 — 회원이고 번호가 맞을 때만 | 첫 조건에서 끝남, 쓰기 없음 |
| `ppx_event_week` | STABLE | 없음 (날짜 계산 한 줄) | 계산만 |
| `ppx_event_start` | IMMUTABLE | 없음 (고정 날짜) | 계산만 |
| `ppx_event_draw_at` | STABLE | 없음 (시각 계산) | 계산만 |
| `ppx_guard` | STABLE | 없음 (SELECT로 건수 세기, 초과 시 오류) | 조회만 |
| `my_pending_count` | STABLE | 없음 (SELECT count) | 조회만 |
| `my_pending_reports` | STABLE | 없음 (SELECT count) | 조회만 |
| `ppx_burst_guard` | VOLATILE | 데이터 쓰기 없음. 트랜잭션 잠금(`pg_advisory_xact_lock`) 사용 | 실행 전 거부 |
| `ppx_stats`, `ppx_event_status`, `is_admin`, `ppx_is_member` | STABLE | 없음 | 조회만 |
| `admin_visit_stats`, `admin_type_votes`, `admin_event_entries` | STABLE | 없음 (운영자 검사 후 SELECT) | 거부 또는 "운영자만" |

- 동적 SQL: 위 함수들에는 없습니다. 42개 중 `delete_my_account` 하나에만 있고 스크립트는 부르지 않습니다.
- 외부 호출(http, dblink 등): 42개 모두 없습니다.
- volatility와 실제 쓰기는 다릅니다. 예를 들어 `ppx_burst_guard`는 VOLATILE이지만 데이터 쓰기가 없습니다. 반대로 STABLE로 선언된 함수는 PostgreSQL이 본문의 쓰기 문장을 실행 시 거부합니다.
